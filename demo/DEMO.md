# MicroPKI — Описание демонстрации

## Что делает демонстрационный скрипт

Скрипт `demo/demo.sh` проводит полный сценарий работы PKI в автоматическом режиме.
Не требует ручного ввода. При каждом запуске использует временный каталог и автоматически очищает его после завершения.

## Запуск

```bash
bash demo/demo.sh
```

## Требования:

- Python 3.10+ с установленным MicroPKI (pip install -e .)
- OpenSSL
- curl

## Шаги демонстрации
### Шаг 1: Создание структуры PKI
Создаются необходимые каталоги (pki/certs, pki/private, pki/crl и др.) и парольные фразы для ключей CA. Парольные фразы записываются в файлы — никакого ручного ввода не требуется.

<strong>Почему это важно</strong>: В реальной PKI структура каталогов и управление секретами — основа безопасности.

### Шаг 2: Корневой УЦ
Создаётся самоподписанный корневой сертификат (RSA-4096, срок 10 лет). Это якорь доверия всей PKI.

Почему это важно: Все остальные сертификаты в конечном счёте доверяются именно корневому CA.

### Шаг 3: Промежуточный УЦ
Создаётся промежуточный CA, подписанный корневым. Именно он будет выпускать конечные сертификаты.

<strong>Почему это важно</strong>: Разделение корневого и промежуточного CA — стандартная практика. Корневой CA можно держать офлайн.

### Шаг 4: Сертификат OCSP-ответчика
Выпускается специальный сертификат для подписи OCSP-ответов (EKU: OCSPSigning).

<strong>Почему это важно</strong>: OCSP-ответчик должен иметь собственный сертификат для подписи ответов о статусе других сертификатов.

### Шаг 5: Серверный сертификат
Выпускается TLS-сертификат для demo.micropki.local (шаблон server, SAN: dns + ip).

<strong>Почему это важно</strong>: Серверные сертификаты используются для защиты HTTPS-соединений.

### Шаг 6: Клиентский сертификат
Выпускается сертификат для аутентификации клиента (шаблон client, SAN: email).

<strong>Почему это важно</strong>: Клиентские сертификаты позволяют реализовать взаимную TLS-аутентификацию (mTLS).

### Шаг 7: Сертификат подписи кода
Выпускается сертификат с EKU codeSigning.

<strong>Почему это важно</strong>: Подпись кода позволяет верифицировать целостность и источник программного обеспечения.

### Шаг 8: Подпись кода и верификация
Python-скрипт demo_script.py подписывается с помощью OpenSSL и закрытого ключа сертификата подписи кода. Затем:

- Подпись верифицируется на оригинальном файле → успех
- Файл модифицируется и верификация повторяется → отказ
<strong>Почему это важно</strong>: Демонстрирует, что подпись защищает от любой модификации файла.

### Шаг 9: Запуск серверов
Запускаются в фоне:

- OCSP-ответчик на порту 8081
- Сервер репозитория сертификатов на порту 8080
### Шаг 10: TLS-демонстрация
Запускается openssl s_server с серверным сертификатом. Затем:

- ```openssl s_client``` подключается с нашим корневым CA → успех
- ```openssl s_client``` подключается без указания CA → отказ
<strong>Почему это важно</strong>: Показывает, что наш сертификат работает для реальных TLS-соединений.

### Шаг 11: Проверка цепочки
```micropki client validate``` проверяет полную цепочку сертификатов: подписи на каждом уровне, сроки действия, BasicConstraints.

### Шаг 12: Отзыв и демонстрация отказа
1. Серверный сертификат отзывается (```keyCompromise```)
2. Генерируется обновлённый CRL
3. OCSP возвращает статус ```revoked```
4. CRL-проверка через ```openssl verify -crl_check``` завершается ошибкой
<strong>Почему это важно</strong>: Отзыв — критически важный механизм PKI для реакции на компрометацию.

### Шаг 13: Применение политик
Три попытки нарушить политику — все отклоняются:

- RSA-1024 (ниже минимума 2048 бит)
- Срок действия 400 дней (максимум 365)
- Wildcard SAN ```*.example.com``` (запрещён по умолчанию)
### Шаг 14: Целостность аудита
```micropki audit verify``` пересчитывает хеш-цепочку всего журнала аудита и подтверждает целостность.

## Ожидаемый вывод
При успешном выполнении все шаги показывают [УСПЕШНО]. В конце выводится итоговый список продемонстрированных возможностей.
